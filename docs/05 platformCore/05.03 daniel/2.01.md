# Platform Core – Architecture Documentation

## Overview

This document describes the architecture of the Platform Core system — a Steam-like gaming platform. The system is structured around an **EventBus** pattern for decoupled communication between components, a generic **Store\<T\>** for persistence, and a **Networking** layer to handle external user connections.

---

## System Architecture Diagram

The architecture consists of the following major components: Record, Store\<T\>, User, Networking, GameSessionManager, GameEngine, GameHistory, EventBus, GameStateUpdate, PlatformCore, MatchMaking, Leaderboard, PartySystem, and stub classes for testing.

---

## Core Components

### (A) Record
The base class for all persistable entities in the system.

| Member | Type | Description |
|---|---|---|
| `id` | int | Unique identifier |
| `Record(int)` | void | Constructor |
| `getID()` | int | Returns the record's ID |
| `setID(int)` | void | Sets the record's ID |

---

### (C) Store\<T\>
A generic, file-backed storage class responsible for persisting instances of `User`, `GameHistory`, and other `Record` subtypes. Each entity type gets its own `Store` instance. Data is written to a stub file (e.g., `SessionsStub`, `GameHistoryStub`) to simulate persistence.

| Member | Type | Description |
|---|---|---|
| `records` | Map | In-memory map of stored records |
| `filePath` | String | Path to the backing stub file |
| `Store(String)` | void | Constructor with file path |
| `find(Predicate)` | List | Query records by predicate |
| `create(T)` | void | Add a new record |
| `delete(T)` | void | Remove a record |
| `update(T)` | void | Update an existing record |
| `loadAll()` | Store\<record\> | Load all records from file |
| `saveAll()` | void | Persist all records to file |

**Key Design Note:** `Store<T>` abstracts all CRUD operations and delegates file I/O to stub files (`SessionsStub` and `GameHistoryStub`). This allows the rest of the system to interact with a clean in-memory API while persistence is handled transparently.

### (A) Networking
The entry point for external users. Handles incoming connections from the internet and routes actions to the rest of the system.

| Member | Type | Description |
|---|---|---|
| `handleConnections()` | void | Accept new connections |
| `syncPlayers()` | void | Synchronise player state |
| `sendPlayerActions()` | void | Forward player input |
| `disconnectPlayer()` | void | Handle disconnects |
| `reconnectToGame()` | void | Reconnect a player to an active session |

### (C) GameSessionManager
Manages the lifecycle of game sessions. It authenticates users, starts and ends sessions, and submits moves to the game engine. It communicates with the **EventBus** — publishing user-submitted events and receiving game events in return.

| Member | Type | Description |
|---|---|---|
| `startSession(roomId, gameType, String)` | String | Start a new game session |
| `submitUserMove(sessionId, playerId, move)` | GameStateUpdate | Submit a player move |
| `respondToUser()` | void | Send response back to user |
| `endSession(sessionId)` | void | Terminate a session |
| `authenticate(login, Password, String)` | void | Authenticate a user |

**Event Flow:** Publishes *User submitted events* → **EventBus** → receives *Game Events* back.

---

### (I) GameEngine
An interface defining the rules and logic for any game type hosted on the platform. Created by `GameSessionManager`.

| Member | Type | Description |
|---|---|---|

| `validateMove(state, move)` | boolean | Check if a move is legal |
| `applyMove(state, move)` | Object | Apply a move, return new state |
| `evaluateEnd(state)` | boolean | Check if the game has ended |

## Event-Driven Components

### (C) EventBus ⭐ *Central Orchestrator*
The **EventBus** is the heart of the platform's communication model. All major system actors publish events to the bus and subscribe to receive events from it. This decouples producers from consumers and allows the system to scale and evolve independently per component.

| Member | Type | Description |
|---|---|---|
| `publish(event)` | void | Broadcast an event to all subscribers |
| `subscribe(handler)` | void | Register a handler for incoming events |

**Event flows through the EventBus:**

| Source | Event Type | Direction | Destination |
|---|---|---|---|
| GameSessionManager | User submitted events | → Bus | EventBus |
| EventBus | Game Events | → Consumer | GameSessionManager |
| MatchMaking | User submitted events | → Bus | EventBus |
| EventBus | MatchPlayer | → Consumer | MatchMaking |
| Leaderboard | List\<Users\> | → Bus | EventBus |
| EventBus | Game Events | → Consumer | GameEngine |
| GameStateUpdate | User submitted events | → Bus | EventBus |
| EventBus | Game Events | → Consumer | GameStateUpdate |

---

### (C) GameStateUpdate
A data transfer object representing the current state of a game, sent to relevant clients after each move.

| Member | Type | Description |
|---|---|---|
| `sessionId` | getSessionID | Session identifier |
| `recipients` | Store\<users\> | Players to receive this update |
| `status` | String | Current game status |
| `activePlayerId` | String | Whose turn it is |
| `payload` | Object | Full serialised game state |

---

### (C) PlatformCore
The final consumer of `GameStateUpdate` events. Responsible for dispatching resolved game state to the appropriate players.

| Member | Type | Description |
|---|---|---|
| `dispatch(event)` | void | Dispatch a game event |
| `notifyPlayer(playerId, msg, String)` | void | Send a message to a specific player |

## Key Architectural Patterns

### 1. EventBus (Observer / Publish-Subscribe)
The `EventBus` completely decouples system components. `GameSessionManager`, `MatchMaking`, `Leaderboard`, and `GameStateUpdate` all communicate exclusively through the bus. No direct references are needed between these classes.

### 2. Generic Store\<T\>
A single, reusable persistence abstraction. Rather than writing custom DAOs for each entity, all `Record` subtypes are managed through `Store<T>`, reducing boilerplate and keeping persistence logic consistent.

### 3. Interface-Based Game Engine
`GameEngine` is defined as an interface `(I)`, allowing any game type (chess, checkers, etc.) to be plugged in without changing the session management or event infrastructure.

### 4. Layered Networking
External users connect through the `Networking` layer, which acts as a firewall between the internet and the platform internals. Only sanitised player actions propagate inward.

## Dependency Summary

```
External User → Networking → GameSessionManager → GameEngine
                                    ↕ (via EventBus)
                          MatchMaking / Leaderboard / GameStateUpdate
                                    ↓
                              PlatformCore → notifyPlayer()
                                    
Store<T> ← User, GameHistory (persisted to SessionsStub / GameHistoryStub)
Record ← User, GameHistory (base class)
```
