# Authentication Flows

## Overview

This document covers the three core authentication flows for the game platform: Login, Logout, and Sign Up. Together these flows define how a player gains access to the platform, ends their session, and creates a new account. All flows interact with a stubbed `CredentialsStore` that will be replaced with a live database connection before release.

---

## 1. Login

### Description

When a player attempts to log in, the GUI collects their username and password and forwards them to `PlatformCore`, which handles the authentication logic. `PlatformCore` delegates credential verification to the `CredentialsStore`, which validates the input and returns an authentication result. Depending on the outcome, the player is either granted access to the game dashboard or shown an error message prompting them to try again.

Passwords are compared against bcrypt hashes stored in the `CredentialsStore`. A loading state is displayed in the GUI while the request is in flight and cleared once a response is received.

### Flow Summary

- The player enters their username and password and clicks Login.
- The GUI displays a loading state and forwards the credentials to `PlatformCore`.
- `PlatformCore` calls `verifyCredentials(username, bcrypt(password))` on the `CredentialsStore`.
- The store returns an `AuthResult` indicating whether the credentials are valid, along with a `userID` if successful.
- On success, `PlatformCore` asks `SessionManager` to create a session, then returns the session token and `userID` to the GUI. The GUI stores the session locally and transitions to the Game Dashboard.
- On failure, `PlatformCore` returns a `loginFailed` response and the GUI displays an error on the login screen.

### Participants

- **Player**: the end user interacting with the login screen.
- **GUI (Welcome/Login)**: handles user input, loading state, and screen transitions.
- **PlatformCore**: the central backend component responsible for authentication logic.
- **SessionManager**: issues session tokens and manages session storage.
- **CredentialsStore (stub)**: validates credentials against hardcoded bcrypt-hashed test accounts.

## 2. Logout

### Description

When a player chooses to log out from the dashboard, the GUI instructs `SessionManager` to invalidate and clear the current session. Once the session is confirmed as cleared, the GUI transitions the player back to the Welcome/Login screen. No interaction with `PlatformCore` or `CredentialsStore` is required for this flow.

### Flow Summary

- The player clicks Logout from the Game Dashboard.
- The GUI calls `clearSession(sessionToken)` on `SessionManager`.
- `SessionManager` invalidates the token server-side and clears any locally stored session data, then confirms to the GUI.
- The GUI transitions the player back to the Welcome/Login screen.

### Participants

- **Player**: the end user initiating the logout action.
- **GUI (Dashboard)**: handles the logout trigger and screen transition.
- **SessionManager**: invalidates the session token and clears local session data.

## 3. Sign Up

### Description

When a new player registers, the GUI collects their username, password, and email and forwards them to `PlatformCore`. `PlatformCore` first checks whether the chosen username is already in use. If it is available, it creates the new account with a bcrypt-hashed password and immediately creates a session so the player is taken directly to the Game Dashboard without needing to log in separately. If the username is taken or an error occurs during account creation, the player is shown an appropriate error on the register screen.

### Flow Summary

- The player enters a username, password, and email and clicks Sign Up.
- The GUI displays a loading state and forwards the details to `PlatformCore`.
- `PlatformCore` calls `checkUsernameAvailable(username)` on the `CredentialsStore`.
- If the username is already taken, `PlatformCore` returns a `registerFailed` response and the GUI shows an error.
- If the username is available, `PlatformCore` calls `createAccount(username, bcrypt(password), email)`.
- On successful creation, `PlatformCore` asks `SessionManager` to create a session, then returns the session token and `userID` to the GUI. The GUI stores the session locally and transitions to the Game Dashboard.
- If account creation fails, the GUI shows a generic error on the register screen.

### Participants

- **Player**: the end user filling in the registration form.
- **GUI (Welcome/Register)**: handles user input, loading state, and screen transitions.
- **PlatformCore**: orchestrates username availability checks and account creation.
- **SessionManager**: issues a session token immediately after successful registration.
- **CredentialsStore (stub)**: checks username availability and stores new accounts with bcrypt-hashed passwords.

## General Notes

- All three flows share the same `SessionManager`, which is the single source of truth for session state across the platform.
- The `CredentialsStore` is currently a stub with no live database connection and must be replaced with a real implementation before release.
- Sign Up intentionally skips the Login step after account creation, logging the player in automatically via a fresh session to reduce friction.
