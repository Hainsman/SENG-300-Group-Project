# Submit Move → Validate → Update Board → Switch Turn

## 1. Objective

This document describes the sequence of interactions that occur when a player submits a move in a multiplayer turn-based game system.

The design ensures:

- Authoritative state control
- Deterministic validation
- Proper turn switching
- Event-driven UI synchronization
- Clean separation of architectural responsibilities

---

## 2. UML Sequence Diagram

```uml
@startuml
title Sequence - Submit Move -> Validate -> Update Board

actor Player
participant "GUI (Game Page)" as GUI
participant "PlatformCore" as Core
participant "GameSessionManager" as GSM
participant "GameEngine (example)" as Engine
participant "EventBus" as Bus

Player -> GUI : select move\nclick Submit
GUI -> Core : submitMove(sessionId, playerId, move, clientStateVersion?)
activate Core
Core -> GSM : submitMove(sessionId, playerId, move)
activate GSM

' Optionally: immediate UI feedback that request was accepted for processing
Core --> GUI : ack(moveReceived)

GSM -> Engine : validateMove(state, move)
activate Engine
Engine --> GSM : valid/invalid + reason?
deactivate Engine

alt invalid
  GSM --> Core : moveRejected(reason)
  Core --> GUI : showMoveRejected(reason)
else valid
  GSM -> Engine : applyMove(state, move)
  activate Engine
  Engine --> GSM : newState (includes nextTurn)
  GSM -> Engine : evaluateEnd(newState)
  Engine --> GSM : ended?/notEnded (+ outcome?)
  deactivate Engine

  alt ended
    GSM ->> Bus : publish(GameEnded(newState, outcome))
  else not ended
    GSM ->> Bus : publish(GameStateUpdate(newState))
  end

  Bus ->> Core : deliver(event)
  Core -> GUI : onEvent(event)
  GUI -> GUI : render updated board\nset input enabled/disabled
end

deactivate GSM
deactivate Core
@enduml
```

---

## 3. Architectural Overview

The system follows a layered and event-driven architecture:

| Component | Responsibility |
|------------|----------------|
| GUI (Game Page) | Handles user interaction and rendering |
| PlatformCore | Coordinates requests and event routing |
| GameSessionManager | Owns authoritative session state |
| GameEngine | Validates and mutates state |
| EventBus | Distributes domain events |

---

## 4. Sequence Explanation

### Step 1 — Move Submission

The player selects a move and submits it via the GUI.  
The GUI sends:

- `sessionId`
- `playerId`
- `move`
- optional `clientStateVersion`

The version parameter supports optimistic concurrency control.

---

### Step 2 — Acknowledgement

PlatformCore acknowledges receipt of the move request.

Purpose:
- Prevent duplicate submissions
- Improve responsiveness
- Indicate processing has started

No validation occurs at this stage.

---

### Step 3 — Session Control

The Core forwards the request to the GameSessionManager (GSM).

The GSM:
- Retrieves authoritative state
- Verifies turn ownership
- Controls mutation boundaries

This ensures a single source of truth.

---

### Step 4 — Validation

The GSM calls:

    validateMove(state, move)

The GameEngine:
- Checks rule legality
- Returns valid or invalid
- May include a rejection reason

If invalid:
- No state mutation occurs
- GUI displays rejection reason

---

### Step 5 — State Mutation

If valid:

    applyMove(state, move)

The GameEngine returns:
- `newState`
- `nextTurn`

State transitions are deterministic and controlled.

---

### Step 6 — End Condition Evaluation

The GSM calls:

    evaluateEnd(newState)

Separating termination logic improves clarity and maintainability.

---

### Step 7 — Event Publication

Depending on outcome:

- `GameEnded`
- `GameStateUpdate`

Events are published asynchronously via the EventBus.

This enables:
- UI updates
- Spectator synchronization
- Lobby notifications
- Analytics extensions

---

### Step 8 — UI Synchronization

The EventBus delivers the event to PlatformCore, which forwards it to the GUI.

The GUI:
- Re-renders board
- Updates turn indicator
- Enables/disables input

The UI reacts to authoritative server events.

---

## 5. Design Properties

### Separation of Concerns
Each component has a single responsibility.

### Deterministic Rule Engine
GameEngine:
- Pure rule evaluation
- No networking logic
- Fully testable in isolation

### Single Source of Truth
Only the GameSessionManager mutates authoritative state.

### Event-Driven Scalability
Additional subscribers can be added without modifying rule logic.

---

## 6. Correctness Guarantees

1. Moves are validated before application.
2. Illegal transitions do not mutate state.
3. Turn switching is controlled centrally.
4. End conditions are explicitly evaluated.
5. UI reflects authoritative state only.

---

## 7. Software Engineering Evaluation

This sequence demonstrates:

- Proper architectural layering
- Strong encapsulation
- Decoupled event-driven communication
- High maintainability and testability
- Scalability for multiplayer environments

It represents a robust and production-ready design pattern for turn-based systems.
