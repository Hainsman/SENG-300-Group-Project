# Turn Notification While Player Is in Lobby/Dashboard

## 1. Objective

This sequence describes how the system notifies a player that it is their turn **even when they are not currently on the game page**.

The key architectural requirement is:

> Game state changes must propagate back to the Platform Core so that the system can notify users regardless of which UI context they are currently viewing.

This design ensures:
- Cross-page state awareness
- Real-time responsiveness
- Decoupled notification handling
- Consistent event-driven architecture

## 3. Architectural Context

This interaction extends the core move-processing flow by demonstrating:

- Event propagation beyond the active game page
- UI-context-aware routing
- Decoupled notification handling

Components involved:

| Component | Responsibility |
|------------|----------------|
| GameGUI | Submits move from game page |
| PlatformCore | Central event router |
| GameSessionManager | Publishes authoritative state updates |
| EventBus | Asynchronous event dispatcher |
| NotificationService | Generates user-facing alerts |
| LobbyGUI | Displays notification banner/badge |

---

## 4. Interaction Explanation

### Step 1 — Other Player Makes a Move

Player P2 submits a move through the game page.

The request flows:

GameGUI → PlatformCore → GameSessionManager

The GSM validates and applies the move (details omitted for clarity).

---

### Step 2 — State Update Publication

After applying the move, the GSM publishes:

    GameStateUpdate(sessionId, stateVersion=V, activePlayerId=P1)

Important properties of this event:

- Contains the authoritative session ID
- Includes a version number (V) for synchronization
- Identifies the next active player (P1)

This event is published asynchronously via the EventBus.

---

### Step 3 — Core Receives Event

The EventBus delivers the event to PlatformCore.

The Core now determines:

- Which player is the active player
- What UI context that player is currently in

This requires session tracking or connection-state awareness.

---

### Step 4 — Conditional Routing

Two possible scenarios:

#### Case A — Player is in Lobby/Dashboard

If P1 is not currently on the game page:

1. Core calls NotificationService
2. NotificationService creates a TurnAlert
3. LobbyGUI receives push notification
4. Lobby displays banner or badge indicator

This ensures that:
- The user is aware it is their turn
- The notification is contextual
- The system remains responsive across pages

---

#### Case B — Player is on Game Page

If P1 is already on the game page:

- The Core may simply route the GameStateUpdate to the GameGUI
- No separate lobby notification is required

This prevents duplicate or redundant alerts.

## 5. Design Principles Demonstrated

### Event-Driven Architecture

State changes are published as domain events rather than directly triggering UI updates.

This enables:
- Multi-context updates
- Spectator support
- Push notifications
- Future mobile integration

---

### UI-Context Awareness

The PlatformCore is responsible for:

- Tracking user connection state
- Routing events based on active UI context
- Avoiding redundant notifications

---

### Separation of Concerns

| Layer | Responsibility |
|--------|----------------|
| GSM | Domain state authority |
| EventBus | Event propagation |
| Core | Routing and coordination |
| NotificationService | Alert generation |
| GUI | Rendering |

No layer mixes domain logic with UI notification logic.

---

## 6. Scalability Benefits

Because notifications are event-driven:

- Mobile push notifications can be added easily
- Email alerts could subscribe to the same event
- Spectators can be notified independently
- Analytics systems can observe turn frequency

No changes are required in the GameEngine.

## 7. Correctness Guarantees

This sequence ensures:

1. Turn changes are derived from authoritative state updates.
2. Notifications are based on server truth, not client assumptions.
3. UI context determines alert behavior.
4. State versioning prevents stale notification display.
5. Cross-page synchronization is maintained.
