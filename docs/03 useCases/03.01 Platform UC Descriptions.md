# Use Case Descriptions #

## About ##

A use case diagram shows what a system does from the user’s perspective, not how it is implemented.

### Purpose ##

Identify who interacts with the system (actors).
Define what goals those actors can accomplish (use cases).
Clarify the system boundary—what is inside the system and what is external.
Provide a shared, high-level understanding for stakeholders (developers, instructors, clients).
Serve as a starting point for requirements, user stories, and test scenarios.

### What it avoids ###

Internal logic, algorithms, data structures.
Execution order or control flow.
UI design details.

### Summary ###

A use case diagram answers “Who can do what with this system?” and is used to scope and validate requirements before design or implementation begins.

### UC-01: View game list ###

Primary actor: Player
Goal: See available games (browse-only).
Preconditions: None (no authentication required)
Trigger: Player visits the welcome page.

Main success scenario:
1. System initializes the Game Menu UI with GameMenuViewData.
2. System displays a list of available games in a list or grid format (e.g., name, icon).
3. System displays navigation options such as View Profile and View Leaderboards.
4. Player browses the list of available games.
5. Player optionally selects a game to view basic information (e.g., game name, description, supported players).
6. Player may choose one of the following actions:
   a. Select a game (triggers navigation to game-specific dashboard or lobby flow).
   b. Navigate to Profile Dashboard.
   c. Navigate to Leaderboards view.

Alternative Flows:
- No Games Available: System displays a message indicating no games are currently available.

Postconditions:
- No game session is created.
- The user hasn’t joined anything
- No matchmaking happened, no lobby joined

### UC-02: Create account ###

Primary actor: Player
Goal: Register a new account.
Preconditions: Player does not already have an account (or chooses to create a new one).

Trigger: Player selects “Create account”.

Main success scenario:
1. System displays registration form.
2. Player enters required details.
3. System validates input and creates the account.
4. System confirms account creation (optionally signs them in).

Alternative Flows:

a. Invalid input
- Validation fails (e.g., missing fields, password mismatch).
- System displays an error message indicating what must be corrected.
- Player updates input and resubmits the form.

b. Account already exists
- Account creation returns FAILURE (e.g., username already in use).
- System displays an appropriate error message.
- Player may choose a different username or return to the Login Page (UC-03)

c. Player cancels account creation
- Player selects “Cancel” or navigates away.
- System returns the player to the Login Page.

Postconditions: Account exists; player is authenticated if auto-login is used.

### UC-03: Log in ###

Primary actor: Player

Goal: Authenticate and access dashboard features.

Preconditions: Player has an account.

Trigger:
Player opens the Login Page.
Player selects “Log in” / submits credentials.

Main Success Scenario:
1. System displays the login form (username & password inputs).
2. Player enters credentials and presses submit.
3. System performs UI-level input validation (fields not empty).
4. System sends credentials to authentication stub, which returns SUCCESS.
5. System redirects player to the Home Page / dashboard.
6. System optionally displays a loading indicator during processing.

Alternative Flow (Failure):
1. Authentication stub responds FAILURE.
2. Login Page displays error message: “Invalid username or password.”
3. Player may:
   a. Correct the input and resubmit credentials (go back to step 2 of Main Success Scenario).
   b. Choose Recover Password → system navigates to Password Recovery UI stub (triggers UC-09: Recover Password).
   c. Player can select “Create New Player” to navigate to the 'Create account' page.

Postconditions:
Player session is established via stub (if login successful).
Player is on the Home Page / dashboard.

### UC-04: View dashboard ###

Primary actor: Player
Goal: Access authenticated options to main home page (lobby, queue, chat, join game when ready).
Preconditions: Player is authenticated.

Trigger: Player logs in or navigates to dashboard.

Main success scenario:
1. System displays the Game Menu / Home Page with:
   a. List of available games (browse-only)
   b. Navigation options: Profile Dashboard, Leaderboards, Settings
   c. Quick status (in lobby, in queue, game ready, leaderboard )

2. Player selects an action:
   a. Choose a game → routed to Game Dashboard or game selection UI
   b. View Profile → routed to Profile Dashboard UI
   c. Show Leaderboards → routed to Leaderboards UI
   d. Open Settings → routed to Settings UI
3. UI updates incrementally as required
4. System optionally shows badges, hints/recommendations for new games or important notifications.

Alternative Flows / Options:
- Player attempts to access a feature that requires updated data → system shows placeholder or loading indicator until data is ready.
- Player clicks a game (triggers UC-06)
- Player selects Profile or Leaderboard → system routes to the appropriate UI stub.
  Postconditions: None.

### UC-05: Join game lobby ###

Primary actor: Player
Goal: Enter a lobby for a specific game (typically to coordinate and chat).
Preconditions: Player is authenticated; target game exists.

Trigger: Player selects a game and chooses “Join lobby”.

Main success scenario:
1. System displays available lobbies (or creates/assigns one).
2. Player is assigned to a lobby:
   a. Player chooses to join a public lobby (can invite friends if allowed).
   b. Player chooses to create a private lobby (triggers UC-10).
3. System displays lobby participants and chat interface.
4. Players can interact via chat; hover over participants to check stats.

Alternative Flows:
- Lobby is full:
  a. System shows “Lobby full” message.
  b. Player is offered UC-06: Enqueue for next available game session.
  c. Player may create their own private lobby (triggers UC-10).
- Lobby no longer available / game canceled: System shows an error message and redirects to the Game Menu.
- Optional leave lobby: Player may leave the lobby anytime before the game starts.
- Network error joining lobby -> UC-12
- Host changes lobby settings after the player joins → system updates lobby view dynamically.

Postconditions: Player is in the selected lobby.

### UC-06: Enqueue for next available game ###

Primary actor: Player
Goal: Wait to be matched/assigned into the next available game session.
Preconditions: Player is authenticated; game supports queueing.

Trigger: Player selects “Enqueue” from the dashboard (optionally choosing a game).

Main success scenario:
1. System places player into the queue.
2. System shows queue status (position, estimated wait, etc. if applicable).
3. When a session is available, the system notifies the player that the game is ready.

Postconditions: Player is either still queued or has a “game ready” status.

### UC-07: Chat ###

Primary actor: Player
Goal: Send/receive chat messages (in a lobby or outside it, if your design allows).
Preconditions: Player is authenticated.

Trigger: Player opens chat UI (from dashboard or lobby).

Main success scenario:
1. Player enters a message.
2. System broadcasts the message to the appropriate channel/context, (other players can view)
3. Player receives messages from others.

Postconditions: Chat history updated (per your design).

### UC-08: Join game ###


Primary actor: Player
Goal: Enter the active game session once it starts.
Preconditions: Player is authenticated;Player is not in queue, a game session is available for the player (invited/matched/ready).

Trigger: Player selects “Join game” after being notified or seeing “game ready”.

Main success scenario:
1. System verifies the player is assigned to the session.
2. System connects the player to the game session.
3. System displays the game.

Postconditions: Player is in an active game session.

### UC-09: Recover Password ###
Primary actor: Player
Goal: Reset a forgotten or lost password to regain access.
Preconditions: Player has an existing account and access to their registered email.
Trigger: Player selects “Recover Password” from Login Page.

Main success scenario:
1. System displays password recovery form.
2. Player enters registered email.
3. System validates email format.
4. System sends password recovery link / code via stub.
5. Player follows link / enters code.
6. System allows player to set new password.
7. System confirms password reset successful.
8. Player can now log in using new password.

Alternative Flows / Options:
- Invalid email → system shows “Email not recognized.”
- Player does not receive email → option to resend.
- Player cancels recovery → returns to Login Page.

Postconditions: Password updated; player can authenticate using new password.

### UC-10: Create Lobby ###
Primary actor: Player
Secondary actors: Invited players (for private lobbies), Other players (for public lobbies), System (stubbed backend)

Goal: Create a lobby for a specific game with configurable access (public or private).

Preconditions:
- Player is authenticated.
- Target game exists.
- Player has permission to create a lobby.
- Player is not currently in another lobby or active game.

Trigger: Player selects “Create Lobby” from the Game Menu or Game Dashboard.

Main success scenario:
1. System displays the Create Lobby form.
2. Player sets lobby options:
    - Lobby name
    - Maximum players
    - Access type: Public or Private
    - Optional password / invite list (for private lobbies)
3. UI feedback: System can suggest max players or default public/private based on game type.
4. Player submits the lobby creation request.
5. System creates the lobby.
6. System displays lobby UI with:
    - Participant list
    - Chat
    - Lobby status
    - Game settings
    - Lobby ID / invite code for private lobbies (stubbed)
7. Players can join according to the access type (private or public)

Alternative flows / enhancements:
- Invalid parameters: System shows error if max players exceeds limits or required fields are empty.
- Lobby creation fails (stub error): System shows error message and allows retry.
- Lobby full: Players attempting to join a full public lobby are offered to enqueue for next available slot UC-.
- Lobby cancellation: Lobby creator leaves before game starts → system auto-closes and notifies participants (stubbed).
- Time-limited lobbies: If lobby idle too long, system auto-closes (stubbed).
- Partial fill start: Lobby creator can start the game before reaching full capacity.
- Modify lobby settings: Creator can toggle public/private, change max players, or update invites.

Postconditions:
- Lobby exists with the selected settings and is displayed to the creator.
- Players can join according to access type and queue rules (simulated / stubbed for Iteration 1).
- Lobby state tracked: OPEN / FULL / IN-GAME / CLOSED (stubbed).

### UC-11: View Game Specific Dashboard ###
Primary actor: Player
Goal: Access a detailed dashboard for a specific game, including matchmaking, leaderboards, and game-specific statistics.
Preconditions: Player is authenticated; player has selected a specific game from the Game Menu / Home Page.
Trigger: Player selects a game → chooses “View Game Dashboard”.

Main success scenario:
1. System displays the Game Dashboard UI for the selected game.
2. Dashboard shows:
   a. Player’s game-specific statistics (wins, losses, rank, achievements).
   b. Leaderboards (top-ranked players).
   c. Matchmaking options (join queue, join lobby, auto-match).
   d. Game session status (active, upcoming, completed).
   e. Navigation to other UI areas (Profile, Leaderboards, Settings).

3. Player can perform actions:
   a. Enqueue for a game session → triggers UC-06.
   b. Join a game lobby → triggers UC-05.
   c. View other players’ stats / hover for detailed info.
4. UI updates dynamically as new stats, leaderboards, or sessions become available.
5. System optionally displays badges, notifications, or recommended matches.

Alternative Flows / Options:
- Player attempts to view stats for a game they haven’t played → system shows placeholder or “No data available”.
- Game session full → system offers to join a similar queue / auto-match (UC-06 stub).
- Network error while loading dashboard → system shows retry or cached data.
- Leaderboard updates → system refreshes dynamically without full reload.

Postconditions: Player is viewing the game-specific dashboard with full access to game-related UI actions.
